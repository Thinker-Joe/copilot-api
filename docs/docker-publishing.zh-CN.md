# 容器镜像发布流程

本文说明 `.github/workflows/release-docker.yml` 的触发条件、验证步骤、镜像标签和构建元数据。

## 触发条件与权限

- 推送匹配 `v*.*.*` 的版本标签后，工作流先执行验证，通过后再向 GHCR 发布镜像。标签推送不按变更文件路径过滤。
- 匹配工作流路径过滤条件的 Pull Request 只执行验证，不登录 GHCR，也不发布镜像。
- 手动触发时，对所选 Git 引用执行验证。只有以 `v` 开头的标签引用允许发布；选择分支不会发布镜像。需要生成版本别名时，应选择有效的语义化版本标签。
- 分支推送不会触发此工作流。
- 工作流默认仅授予 `contents: read` 权限，只有发布任务具有 `packages: write` 权限。

## 发布前验证

Linux AMD64 和 ARM64 两个原生运行器上的任务必须全部成功。每个任务按锁文件安装根目录及桌面端依赖，执行 `bun run lint:all`、`bun run typecheck:all` 和 `bun test`，然后构建本地镜像。

以下附加检查取决于所选版本中是否包含相应文件：

- 存在 `docker-compose.yaml` 时，校验基础 Compose 配置；同时存在 `docker-compose.bind.yaml` 时，再校验合并后的配置。
- 存在 `tests/docker-smoke.test.ts` 时，通过 `COPILOT_API_DOCKER_TEST_IMAGE` 指定本地镜像并运行该测试。

缺少这些文件时，相应检查会跳过。镜像构建成功本身不代表容器生命周期行为已通过验证。

## 镜像地址与构建元数据

镜像发布到 `ghcr.io/<owner>/<repository>`，仓库标识统一转换为小写。

验证通过后，发布任务使用 Buildx 和 QEMU 构建并推送包含 `linux/amd64` 和 `linux/arm64` 的多平台镜像。这是一次独立构建，并非直接发布验证任务生成的本地镜像。

构建启用 SBOM 和 `mode=max` provenance 证明，用于描述镜像内容和构建输入。这些元数据不等同于镜像签名或漏洞扫描结果；本工作流不对镜像签名。

## 镜像标签

以下使用假设的版本标签举例：

| Git 标签 | 镜像标签 |
| --- | --- |
| `v2.5.3` | `v2.5.3`、`v2.5`、`v2`、`2.5.3`、`2.5`、`2`、`latest`、`sha-<完整提交 SHA>` |
| `v2.6.0-beta.1` | `v2.6.0-beta.1`、`2.6.0-beta.1`、`sha-<完整提交 SHA>` |

稳定版同时生成带 `v` 前缀和不带前缀的版本别名。预发布版只生成完整版本标签和提交标签，不更新主版本、次版本或 `latest` 别名。显式设置 `prefix=v`，确保预发布标签也保留该前缀。

所有标签（包括 `sha-*`）都可能被后续发布覆盖。部署需要固定到不可变的镜像内容时，应使用镜像摘要。

## 并发与重新运行

并发组按 Git 引用隔离。不同版本标签的任务不会相互取消；同一标签的新任务也不会取消正在运行的任务。

发布稳定版时会更新其滚动别名，包括 `latest`，但不会检查该版本是否高于先前发布的版本。因此，重新发布旧稳定版可能使这些别名回退；不同引用的发布任务也可能不按版本顺序完成。重新运行或手动触发发布前，应确认所选标签。
